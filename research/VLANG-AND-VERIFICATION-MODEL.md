# VORAX — V-Lang and the verification model

**Evidence snapshot:** 25 November 2026  
**Primary sources:** `VLANG_V1.md`, `docs/TLANG_V1.md`, `vorax/tlang.py`, `vorax/vlang.py`, `vorax/engine.py` and `scripts/verify_library.py`.

## 1. Why V-Lang exists

V-Lang is a constrained data format for describing bounded procedures. It is intentionally not Python, JavaScript, shell, an arbitrary prompt, or a model checkpoint.

The purpose is to turn a proposed capability invocation into a typed, inspectable, testable record that a trusted Runtime can validate and execute through an allowlisted interpreter.

A method is not accepted because a teacher says it is correct. It is accepted only after it passes syntax, type, operation, provenance and test requirements and enters the trusted Home review workflow.

## 2. Record format

V-Lang v1 uses one JSON object per non-empty line. A record contains exactly:

- `version`
- `id`
- `domain`
- `task`
- `triggers`
- `inputs`
- `steps`
- `result`
- `tests`
- `provenance`

New writes use `version: "vlang/1"`. The reader supports the legacy `tlang/1` version for compatibility, but new writes are V-Lang.

Input types are bounded to number, integer, string, boolean and number_list.

Each method is limited to 1–20 steps and must include 2–20 executable test vectors. Home re-runs the verifier before an approved method is accepted.

## 3. Deterministic operations

The inspected interpreter exposes bounded operations such as:

- arithmetic and percentages;
- average, minimum and maximum;
- sorting, uniqueness and counting;
- word counting and string transformations;
- unit conversions;
- boolean logic and comparisons;
- absolute/rounding operations;
- deterministic intent classification.

The operation list is defined in the language implementation, not supplied freely by a candidate. Unknown operations are rejected.

## 4. Registered tool calls

V-Lang supports a constrained `call_tool` instruction for a server-registered tool. The language's declared registry includes tool contracts for:

- `image.generate`
- `audio.tts`
- `audio.transcribe`
- `video.generate`
- `music.generate`
- `translate`
- `code.execute`

A candidate cannot choose an arbitrary URL, provider, model ID, shell command, Python code or unregistered tool. Runtime checks the tool registry again at execution time.

The existence of a tool name/schema does not prove that its real external adapter is configured or that a live media artifact can be generated. A Home validation contract stub tests the tool name and arguments; a real artifact is only successful if a registered adapter returns an explicitly verified result and the artifact passes verification.

## 5. Validation stages

A candidate method is checked in layers:

1. JSON shape and exact allowed keys.
2. Version and stable identifier format.
3. Typed input schema.
4. Bounded step count and supported operations.
5. Valid input/previous-step references; no forward references.
6. Registered tool name and argument schema, if called.
7. Privacy/secret patterns and provenance metadata.
8. Execution of each declared test vector.
9. Duplicate method checks against Home metadata.
10. Trusted Home verifier and human review before approval.

This layered approach reduces risk, but it does not prove all possible input combinations are correct.

## 6. What a passing test actually proves

Suppose a method contains two tests:

- test A: input values 5 and 4 produce 20;
- test B: input values 2.5 and 8 produce 20.

If both pass, the verifier has shown that the interpreter produced the declared expected outputs for those two cases, using that method record and implementation.

It has **not** proven:

- correctness for every valid number;
- absence of every edge case;
- mathematical truth for all possible inputs;
- appropriateness for safety-critical decisions;
- that a real external artifact was generated by a mocked tool contract;
- that the external service will remain available;
- that a source's claims are authoritative.

For high-impact tasks, VORAX would require stronger domain validation and authoritative evidence than a small set of example vectors.

## 7. Unknown and ambiguity are valid states

The engine returns unknown when no verified method matches. It can also return ambiguous when multiple methods tie, or input_required when a method cannot run with the supplied fields.

This is intentional. The system must not silently fall back to an invented answer and represent it as verified execution.

Input X's inspected classifier is itself a Home V-Lang procedure. If that classifier is missing or fails, the system returns unknown rather than substituting a neural classifier.

## 8. Compatibility and migration

V-Lang is the current write format. Legacy T-Lang records remain readable for migration compatibility. Do not introduce a second competing method schema or bypass the canonical parser.

The metadata-only Home index currently lists 30 records in the inspected main-branch snapshot. That is a repository count, not a benchmark of task coverage, correctness or production capability. It can change as the library evolves.

## 9. Security constraints in the language

The interpreter disallows arbitrary loops, recursion, dynamic evaluation, file/network access and executable source. Values must be literals or references to declared inputs/previous steps. It includes pattern checks against common credential and personal-data formats.

These controls reduce the expressiveness of the language by design. This is an intentional trade-off: VORAX prioritizes inspectability and constrained execution over unrestricted computation.
